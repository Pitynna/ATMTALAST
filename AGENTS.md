# Правила проекта ATMTALAST

Рабочая папка и репозиторий — только этот каталог (`Z:\ATMTA\ATMTALAST`,
GitHub `Pitynna/ATMTALAST`). Не создавайте рядом копии проекта, «запасные»
каталоги и параллельные клоны.

## Сначала прочитать и применить правила

- **Первое действие в новой задаче — прочитать актуальные `AGENTS.md` от
  рабочего каталога до каталога изменяемых файлов.** Сделайте это до изменений,
  сборок, запуска скриптов и серверов. Для чата из `Z:\ATMTA` обязательно
  прочитать `Z:\ATMTA\AGENTS.md` и этот файл. Для вложенных каталогов найти
  дополнительные `AGENTS.md` и применить их к соответствующим файлам.
- После восстановления контекста, смены проекта или сообщения пользователя
  об изменении правил перечитать применимые инструкции. Память о прошлой
  версии правил и пересказ другого агента не заменяют чтение текущего файла.
- До выполнения действия проверить его по этим правилам. Нарушающий их
  способ работы заменить безопасным; не оправдывать нарушение удобством,
  скоростью или тем, что подобный запуск раньше проходил успешно.
- Перед работой проверить текущую ветку, `git status`, staged-изменения и
  отсутствующие отслеживаемые файлы. Не считать рабочую папку чистой или
  полной по памяти о предыдущем запуске.

## Сохранение работы (обязательно)

6 ноября 2026 вся несохранённая работа (астероид, ксеноархеология, Ulthor и
др.) была потеряна: в `tmp` лежали ссылки (junction) на `code`, `_maps`,
`icons` и другие папки проекта, и рекурсивное удаление `tmp` стёрло оригиналы.
Из-за этого:

1. **После каждой крупной задачи (и после каждого завершённого этапа внутри
   большой) делайте коммит и заливайте на GitHub (`git push`).** Не оставляйте
   сделанное только в рабочей папке. Если задача длинная — коммитьте и
   пушьте не реже чем раз в час работы.
2. Работайте в отдельной ветке (`codex/...` или `claude/...`), не в `master220`.
   Перед слиянием в `master220` ветка должна компилироваться без ошибок.
3. Перед коммитом проверяйте, что новые файлы не попали под `.gitignore`
   (`git status`, `git check-ignore -v <файл>`); исходники должны быть в коммите.
4. Скрипты и результаты проверок, которые нужны надолго, храните в `tools/`
   или `docs/`, а не только в `tmp/` (`tmp/` в `.gitignore` и не сохраняется).
5. **До первого потенциально разрушающего действия, включая запуск сервера
   или чужого проверочного скрипта, сохранить текущую работу.** Собственные
   завершённые изменения закоммитить и отправить на GitHub. Существующие
   незакоммиченные изменения, которые нельзя включать в свой коммит, сохранить
   отдельно вместе с новыми файлами и проверить содержимое копии. Копия должна
   находиться вне всех каталогов, которые запускаемый код может очищать;
   `tmp/` и `data/` для такой страховки не использовать.
6. При параллельной работе учитывать, что ветка, рабочие файлы и Git index
   общие. Добавлять в коммит явный список собственных файлов, проверять
   staged diff непосредственно перед коммитом. Не включать чужие staged
   изменения, не сбрасывать их и не переключать общую ветку без координации.
   Проверять результат `commit` и `push`; локальная запись без успешного
   `push` не считается сохранением на GitHub.

## Запрещено

- Создавать junction/symlink на папки проекта (`code`, `_maps`, `icons`,
  `interface`, `html`, `sound`, `strings`, `tgui`, `SQL`). Для изолированных
  прогонов копируйте нужные файлы или запускайте сборку прямо в проекте.
- Очищать целиком `tmp/`, `data/` или каталоги исходников при запуске,
  остановке и проверках. В частности, **`fdel("tmp/")` запрещён**: его
  вызов из скомпилированного сервера тоже может пройти по junction-ссылкам.
  Создатель временного файла удаляет только конкретные файлы, которыми владеет.
- Удалять каталоги рекурсивно (`Remove-Item -Recurse`, `rd /s`, `rm -rf`,
  `shutil.rmtree`, BYOND `fdel` каталога) без предварительной проверки
  абсолютного пути, всех его компонентов и содержимого. Цель должна быть
  конкретным собственным каталогом артефактов внутри разрешённой области.
  Проверять reparse points через `lstat`/`os.scandir` с
  `follow_symlinks=False`, **не переходя по ссылкам**. Одного `resolve()`,
  проверки имени `tmp` или обычного рекурсивного обхода недостаточно.
  При обнаружении любой ссылки остановить удаление и сначала разобраться
  с ней; не пытаться «почистить» её содержимое.
- `git clean`, `git reset --hard`, `git checkout -- .` и любые команды,
  затирающие незакоммиченные изменения, без коммита/копии перед этим.

## Перед запуском скрипта или игрового сервера

1. Прочитать код запускаемых проектных скриптов и относящиеся к запуску
   операции с файлами. Для сервера проверить также инициализацию и завершение
   работы, включая `code/controllers/subsystem/server_maint.dm`. Найти
   создание ссылок и очистку каталогов: `Junction`, `SymbolicLink`, `mklink`,
   `symlink`, `Remove-Item`, `rmtree`, `fdel` и аналогичные вызовы. Учесть
   вызываемые ими проектные скрипты. Сборка и запуск сервера — разные действия;
   успешная компиляция не доказывает безопасность запуска.
2. Проверить `tmp/` и каталоги проверочного запуска на reparse points без
   перехода по ссылкам. При наличии ссылок на проект не запускать этот runtime.
   Проверочные окружения создаются копированием нужных файлов либо запуском
   из проекта, без junction/symlink на его каталоги.
3. Зафиксировать сохранность отслеживаемых и новых рабочих файлов, выполнить
   требования сохранения выше. Если уже есть необъяснимые удаления, сначала
   разобраться с ними; не запускать сервер для «проверки» повреждённого дерева.
4. Если исправлялась опасная операция, **пересобрать бинарник до запуска**.
   Изменение `.dm` не меняет старый `.dmb`; запуск старого бинарника способен
   повторить удаление. Не запускать заведомо опасный старый бинарник даже
   ради воспроизведения. При изменении очистки проверять запуск и завершение
   на обычных вложенных файлах, без создания опасных ссылок для теста.
5. После запуска сравнить сохранность файлов с состоянием до него и проверить
   журнал ошибок. При новых исчезновениях сразу остановить запущенный собой
   процесс, сохранить сведения об инциденте вне очищаемых каталогов и найти
   причину. Не продолжать повторные запуски и восстановления наугад.
